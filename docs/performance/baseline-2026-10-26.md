# Portfolio performance analysis — 26 October 2026

The animated sky is the main performance cost. The city images are the second largest loading cost, but they are much cheaper once displayed. The opening's detailed drawings, name animation and small pulses are a minor part of the download; removing them would leave the principal cost in place.

**Historical baseline:** captured before the accepted optimization release; local/unpublished statements below describe the audit date. Current behavior and decisions are indexed in README.md.

This audit uses the diagnosing-bugs skill's measured baseline and one-variable comparisons. It is an analysis of the accepted design, not a redesign. Public remains97121cc at alghuraid.com. The prior loading/viewer fixes and this audit's small image optimization remain local and unpublished.

## What the percentages mean

There is no single honest “percentage of website performance.” Downloading files, running JavaScript, drawing frames and retaining memory are separate costs. A downloaded image may be large but require almost no continuous work; a tiny animation can redraw constantly.

The table below divides **13,906,933 bytes of measured resource bodies** in the pinned published desktop homepage run. These are sizes after HTTP decompression, before decoding image pixels or GPU textures. They are not live CDN transfer bytes, CPU percentages, battery use, or percentages of the device's capacity. Main HTML and iframe subresources are outside this parent ResourceTiming sum; cached/cross-origin resource reporting can vary. [W3C Resource Timing](https://www.w3.org/TR/resource-timing/) defines these distinctions.

| Part | Body weight | Share | Practical meaning |
| --- | ---: | ---: | --- |
| Sky/cloud renderer, atmosphere/cloud data and moon | 9.35 MB | **67.2%** | Largest loading cost and principal continuous rendering cost |
| Day + night city images | 4.07 MB | **29.3%** | Large loading/decode cost; composition updates on blend changes rather than every frame |
| Initial still scene poster | 0.20 MB | **1.4%** | Small, useful cover while the real scene initializes |
| Opening artwork script + stylesheet | 0.051 MB | **0.4%** | Detailed appearance with a small file footprint; short-lived motion |
| Other measured styles, scripts, text, etc. | 0.244 MB | **1.8%** | Includes navigation, language and interaction code; rounding makes total100.1% |

The atmosphere scattering file alone is4.09MB (~29.4% of this total), cloud shape data2.10MB (~15.1%), sky engine JavaScript0.86MB (~6.2%), and another noise dataset1.05MB (~7.5%). These are more consequential loading targets than button icons or labels.

## Startup: the biggest interruption

The published-source desktop trace contained a1,071ms main-thread task attributed by the browser's long-animation-frame script data to sky.js. Other working runs showed roughly0.8–0.9seconds in the same startup region. A calibration run with the expensive WebGL/animation callback wrappers disabled still showed799ms; the interruption is not solely created by instrumentation.

The390×844 browser test still showed an885ms startup task. Rendering fewer pixels therefore does not remove all initialization work. The code loads/decompresses atmosphere and cloud data, creates textures and prepares the scene. The exact split between parsing, data conversion and driver work needs a deeper trace before choosing a worker or precomputation strategy. Shader compile/link wrapper time alone did not explain it; browser/driver work may be deferred.

In the isolated still-poster comparison, sky AND city initialization were bypassed: no tasks over50ms were recorded, no WebGL context existed and measured body weight was0.56MB. That is evidence that the expensive scene path matters. It is **not** a recommendation to replace the accepted scene or proof that every startup millisecond is caused by clouds alone.

The opening can be visible while this separate background setup runs. That explains how a lightweight loading animation can appear to stutter: other work blocks its browser thread. The previous issue56 first-paint/hold fix addresses when the opening appears; it does not make the sky initialization cheaper.

## Ongoing drawing: where most animation work goes

Same desktop viewport1779×1292, DPR1, NVIDIA RTX3080. Twelve GPU timing samples per instrumented comparison; single-run comparisons give direction, not laboratory confidence intervals.

| Local comparison | Median GPU time per scene frame | Estimated known texture allocations | Draw calls during ~4 seconds |
| --- | ---: | ---: | ---: |
| Current local desktop, high sky quality | **4.30ms** | **141MB** | 4,907 |
| Medium sky quality at same desktop size | **2.08ms** | **112MB** | 5,187 |
| Paused scene movement | **4.22ms** | **141MB** | 5,180 |
| Full rendering freeze | No valid drawing sample | **141MB retained** | **0** |

Medium used approximately **52% less GPU time per frame** and **21% fewer known texture bytes** in these samples. This is not a52% faster website. Files downloaded remain essentially the same; visual quality and startup work need separate review. Phone width already selects medium in the current code.

The sky uses about seven drawing passes per scene frame and follows the display animation loop. It submitted roughly150–185 scene frames/second in these desktop runs. The accepted effect may not need that frequency. A60fps cap could reduce submissions on high-refresh displays;30fps may reduce them further, with a visible motion tradeoff. Neither percentage savings nor smoothness should be assumed before measuring an implementation.

**Confirmed inefficiency:** paused mode stops simulation movement but continues full rendering. In the freeze comparison, sky callback CPU time fell from381ms to6.4ms across the four-second window, and draw calls fell to zero. A pause fix should render again on theme/time/resize changes, not blindly freeze all state. Reduced-motion code follows a similar static-time path and deserves the same review.

Current hidden-document early returns and project-navigation freeze are already helpful. Navigation retains the home scene to avoid a reload and scroll/background discontinuities. This saves repeated initialization at the cost of retaining textures while a project is open. Disposing them would need careful return-home testing.

GPU timing is asynchronous drawing time, not utilization percentage. Texture figures estimate tracked live texture storage only; they exclude some renderbuffers, driver overhead and other browser memory. JavaScript heap figures are also not total tab RAM. [Chrome's long-animation-frame documentation](https://developer.chrome.com/docs/web-platform/long-animation-frames) explains the limits of script attribution.

## City, projects and smaller interactions

- **City:** both day/night images load for smooth theme blending. Each decodes to about6.3MB of RGBA pixels, plus intermediate canvases and preparation buffers. Existing code avoids recomposing when the blend is unchanged. Preserve that accepted compositing and skyline silhouette.
- **Project/program pages:** source uses a static editorial background rather than starting another WebGL sky. A direct n8n project sample had0WebGL contexts, no tasks over50ms, and about141KB of parent resource bodies before its lazy screenshots were needed. This is not the complete page download or a live network timing. Screenshots are the larger project assets: n8n's three are roughly193/254/220KB; TrackFlow390/361KB; the cloud program's largest screenshot806KB. Viewers can add decoding/memory cost only when used.
- **Diagrams:** four homepage iframe documents were present before scrolling in the desktop run despite lazy loading. Desktop reported37 running internal animations while those frames were offscreen; the phone-size run reported0. Browser culling can reduce actual paint cost, so the count alone does not prove a large CPU cost. Explicit visibility-based pause/deferred mounting is a lower-priority experiment. A sampled project had visible and offscreen diagram animations too.
- **Opening:** the script/stylesheet total is about51KB, not counting shared fonts/styles. Its few transform/opacity pulses finish when the intro leaves. No evidence here supports removing its accepted artwork to solve the main performance issue.
- **Cards, text, language/theme controls and Back:** relatively small scripts and mostly interaction-driven work. Their layout/paint during a transition matters to polish, but they are not the main idle load. CV files download on demand, not with the homepage.
- **Small duplication:** translations.json is requested twice in the no-store audit (~18KB each). Production caching may avoid a second transfer. Share one request eventually, but it is a small gain relative to megabytes of scene data.
- **Poster preload:** some local runs exposed two entries for the same195KB poster, unlike the pinned baseline. Check preload/image request matching and cache behavior on the actual release network before claiming a duplicate transfer bug.

## Safe change applied locally

Optimized the existing two PNGs without changing their dimensions, alpha edges or browser-rendered pixels. Fully transparent hidden RGB was normalized and PNG compression improved; original metadata was retained. Browser canvas comparisons found **zero changed channels** across6,294,240 daytime and6,290,480 nighttime channels.

| Image | Before | After | Saving |
| --- | ---: | ---: | ---: |
| Day skyline | 2,148,795 B | 2,034,152 B | 5.3% |
| Night skyline | 1,920,022 B | 1,869,810 B | 2.6% |
| Combined | 4,068,817 B | 3,903,962 B | **164,855 B / 4.1%** |

This saves about **1.2% of the measured homepage body weight**. It reduces loading bytes, not ongoing sky rendering or decoded city dimensions. A larger26–31% WebP candidate was rejected after browser-decoded pixel differences, despite an earlier image-library equality check. Originals/rejected experiments are kept in scratch; no rejected assets or audit scripts remain in public source.

## Recommended order

1. Keep the verified image saving; it preserves the design. It remains unpublished with the earlier issue56 fixes.
2. Prototype a sky frame-rate cap and true paused/reduced-motion render-on-change. Test theme changes, resize, project Back and the opening handoff before adoption. Strong ongoing-cost opportunity with minimal intended visual change.
3. Compare medium and high desktop sky quality visually. Measured GPU savings are substantial; preserve the preferred appearance unless the tradeoff is acceptable.
4. Trace the long startup task more deeply. Evaluate preprocessed atmosphere data or moving eligible conversion work off the main thread. Moving only the start time can hide/block at a different moment without reducing work.
5. Inspect whether all cloud/noise textures and HDR targets need their current precision/resolution. This is deeper renderer work and needs visual regression testing; do not blindly compress scientific data files as ordinary images.
6. Then address offscreen diagrams, request sharing and preload matching. Avoid spending the first optimization round on inexpensive buttons, CV links or the opening drawings.

## Evidence and limits

Raw runs: `../opening-performance/audit-*.json`. Arithmetic: `summarize.cjs` → `summary.json`. Local server/probe: `serve-audit.cjs` and `probe.js`; never included in the public build. PNG candidate metadata: `png-image-candidates.json`; browser pixel check page: `image-check.html`.

Measured published-source baseline, current local version, medium-quality, paused, frozen and still-poster variants; calibration without rendering wrappers;390×844 responsive viewport and a representative n8n direct detail page. Browser viewport tests use this desktop's GPU and DPR1, **not physical phone CPU, battery or thermal behavior**. Most samples use English/night; a complete language/theme/device performance matrix was not run. Cold driver/font caches vary. Local server uses no-store and no response compression, so its wall-clock load times and body weights must not be presented as visitors' cellular download times. The baseline was captured before PNG optimization; the later phone run uses optimized PNGs. No live instrumentation, production change, commit, push or deployment occurred.

Build and release reference/syntax checks pass after the PNG change. A physical mid-range phone and live cold/warm network trace are the next validation steps before claiming a general mobile performance improvement.
